# create-pr

현재 브랜치가 기본 브랜치에 비해 무엇을 바꿨는지 읽고, 템플릿에 맞춰 PR 본문을 채워 GitHub PR을 만든다. 사용자가 이 스킬을 부른 것 자체가 push와 PR 생성을 해도 좋다는 뜻이다.

이 스킬은 `context: fork`로 실행되어 대화 기록을 볼 수 없다. 변경의 의도는 전부 git 기록(커밋 메시지, diff, 브랜치명)과 호출 인자에서 찾는다. 그래서 커밋 메시지에 없는 이유를 추측해서 쓰지 않는다. 모르는 것은 본문에서 빼는 편이 틀린 설명을 남기는 것보다 낫다.

사용할 수 있는 도구는 Read, Glob, Grep, Bash뿐이다. 파일 쓰기 도구가 없으므로 본문은 파일로 저장하지 않고 `gh`의 stdin으로 넘긴다.

## 인자

호출 인자에서 아래를 읽는다. 모두 선택이다.

| 인자 | 의미 | 기본값 |
| --- | --- | --- |
| `en` | 이번 PR만 영어 템플릿 사용 | 한글 템플릿 |
| `--base <브랜치>` | PR 대상 브랜치 | 저장소 기본 브랜치 |
| `--draft` | draft PR로 생성 | 일반 PR |
| `--dry-run` 또는 "미리보기" | push와 PR 생성 없이 제목과 본문만 출력 | 실행 |

그 외의 자유 문장(예: "로그인 개선 건이야")은 변경 배경에 대한 사용자의 설명으로 보고 본문 요약에 반영한다.

## 절차

### 1. 상태 확인

서로 독립적이므로 한 번에 실행한다.

```bash
git branch --show-current
git status --short
git symbolic-ref --short refs/remotes/origin/HEAD   # 기본 브랜치 (예: origin/main)
gh auth status
```

다음 경우에는 이유를 알리고 멈춘다.

- git 저장소가 아니다.
- 현재 브랜치가 기본 브랜치(`main`, `master` 등)다. 기본 브랜치에서 자기 자신으로 PR을 만들 수 없다. 작업 브랜치를 만들어 커밋한 뒤 다시 호출하라고 안내한다.
- detached HEAD다.
- `gh`가 없거나 인증되어 있지 않다. 인증은 사용자가 직접 해야 하므로 `! gh auth login`을 안내한다.

`origin/HEAD`가 없으면 `gh repo view --json defaultBranchRef -q .defaultBranch`로 기본 브랜치를 얻는다. 이 저장소가 GitHub Enterprise여도 `gh`는 remote 호스트를 보고 알아서 맞추므로 호스트를 따로 지정하지 않는다.

커밋되지 않은 변경(`git status --short` 출력이 있음)은 PR에 들어가지 않는다. 이 스킬은 그 변경을 대신 커밋하지도 않는다. 의도하지 않은 파일이 PR에 섞이는 것을 막기 위해서다. 최종 보고에 "커밋되지 않은 변경 N개가 PR에 포함되지 않았다"고 적고, 커밋이 필요하면 `commit` 스킬을 쓰라고 안내한다.

### 2. 이미 열린 PR 확인

```bash
gh pr list --head <현재 브랜치> --state open --json number,url,title
```

이미 있으면 새로 만들지 않는다. 기존 PR의 URL을 알리고, 본문을 갱신할지는 사용자에게 맡기고 멈춘다. 같은 브랜치의 PR이 중복되면 리뷰가 갈라지기 때문이다.

### 3. 변경 분석

기준은 기본 브랜치와의 **분기점 이후**의 변경이다. 세 점(`...`) 표기를 쓴다. 기본 브랜치가 그 사이에 앞서갔더라도 이 브랜치가 만든 변경만 보이게 하기 위해서다.

```bash
git log --oneline <base>..HEAD
git diff <base>...HEAD --stat
git diff <base>...HEAD
```

`<base>`는 로컬 브랜치가 뒤처져 있을 수 있으므로 `origin/<기본 브랜치>`를 쓴다. 필요하면 `git fetch origin <기본 브랜치>`를 먼저 실행한다.

- 커밋이 0개면 PR로 보낼 것이 없다고 알리고 멈춘다.
- diff가 크면 `--stat`으로 윤곽을 잡고 파일별로 나눠 읽는다.
- 읽는 목적은 파일 목록을 만드는 것이 아니라 **무엇을 왜 바꿨는지** 이해하는 것이다. 커밋 본문과 diff의 변경 이유를 단서로 삼는다.
- 프로젝트 루트의 `AGENTS.md`, `CLAUDE.md`가 있으면 읽는다. 검증 명령(lint, test, build)과 PR·커밋 관례가 거기 적혀 있는 경우가 많다.

### 4. 템플릿 선택

**저장소 자체의 PR 템플릿이 있으면 그것을 먼저 쓴다.** 팀이 정한 양식이 개인 전역 템플릿보다 우선이다. 아래를 이 순서로 찾아 처음 나온 것을 쓴다.

```
.github/pull_request_template.md
.github/PULL_REQUEST_TEMPLATE.md
.github/PULL_REQUEST_TEMPLATE/ 아래의 파일
docs/pull_request_template.md
pull_request_template.md
```

저장소 템플릿이 있으면 그 섹션 구조를 그대로 채우고, 본문 언어는 템플릿의 언어를 따른다.

없으면 한글 템플릿 `~/.claude/references/pr-template.ko.md`를 Read로 읽는다. 이 프로젝트는 PR을 한글로 쓰기로 했으므로 커밋 메시지 언어를 따져 보지 않고 항상 한글을 쓴다. 인자에 `en`이 명시된 경우에만 `~/.claude/references/pr-template.en.md`를 쓴다.

템플릿 파일이 없거나 읽을 수 없으면 임의의 양식으로 대체하지 말고, 경로를 알리고 멈춘다. 사용자가 템플릿을 의도해서 관리하고 있으므로, 조용히 다른 양식으로 만들면 의도를 깨뜨린다.

### 5. 제목과 본문 작성

**제목**

- 형식은 `<type>: <요약>`. type은 `feat`, `fix`, `refactor`, `chore` 중에서 고른다. 단, `git log`가 다른 type을 일관되게 쓰고 있으면 저장소 관례를 따른다.
- 템플릿 언어와 맞춰 한글 템플릿이면 한국어로, 영어 템플릿이면 영어로 쓴다. 70자 안팎의 한 줄이고 마침표는 붙이지 않는다.
- 브랜치의 커밋이 여러 목적을 섞고 있어도 PR 전체를 대표하는 하나의 요약을 쓴다. 단일 커밋 PR이면 그 커밋 제목을 그대로 쓰는 것이 자연스럽다.
- 이슈 번호는 브랜치명이나 커밋에서 명확히 읽힐 때만 넣는다. 추측해서 만들지 않는다.

**본문**

템플릿의 섹션 구조와 순서를 유지하고 각 섹션을 채운다. 주석(`<!-- -->`)은 작성 지침이므로 최종 본문에서 모두 지운다.

- 요약은 변경 이유를 먼저, 그다음 무엇을 했는지 쓴다. 리뷰어가 diff를 열기 전에 맥락을 잡게 하는 것이 목적이다.
- 변경 사항은 파일 나열이 아니라 동작·구조의 변화로 쓴다. 파일명은 리뷰어가 diff에서 이미 본다.
- **테스트 섹션은 실제로 확인된 것만 체크한다.** 이 스킬은 테스트를 실행하지 않고 커밋 기록에도 결과가 없으므로, 근거가 없는 항목은 체크하지 않고 비워 둔다. 체크된 항목은 리뷰어가 "검증됨"으로 읽기 때문에, 근거 없이 체크하면 리뷰어를 속이는 일이 된다. 사용자가 인자로 "테스트 통과 확인함"이라고 알려 줬다면 그 범위만 체크한다. `AGENTS.md`에 이 저장소의 검증 명령이 있으면 항목 이름을 그에 맞게 바꾼다.
- 해당 내용이 없는 섹션(관련 이슈, 리뷰어 참고 등)은 빈 채로 두지 말고 섹션째 지운다.
- 본문에 비밀번호, API 키, 토큰, 개인정보가 들어가지 않게 한다. diff에서 그런 값이 보이면 본문에 옮기지 말고, 최종 보고에서 **값은 인용하지 말고 파일명과 줄 번호만** 알린다. 그 값이 커밋에 들어 있는 상태로 PR을 만들면 외부에 노출되므로 이 경우는 PR을 만들지 않고 멈춘다.
- 사실과 추정을 구분한다. diff에서 확인한 것은 단정하고, 의도를 짐작한 것은 "~로 보인다"로 쓴다.

### 6. push와 PR 생성

`--dry-run`이면 제목과 본문을 출력하고 여기서 끝낸다.

그렇지 않으면 upstream 여부를 확인해 push한다.

```bash
git rev-parse --abbrev-ref --symbolic-full-name @{u}   # 실패하면 upstream 없음
git push -u origin <현재 브랜치>
```

- upstream이 이미 있고 로컬이 앞서 있으면 `git push`만 한다.
- **force push는 하지 않는다.** 원격과 갈라져 push가 거절되면 상황을 설명하고 멈춘다. 다른 사람의 커밋을 덮어쓸 수 있고 되돌리기 어렵기 때문이다.

본문은 heredoc으로 stdin에 넘긴다. 셸 인용 문제로 본문이 깨지는 것을 막으려고 구분자를 따옴표로 감싼다.

```bash
gh pr create --base <기본 브랜치> --title "<제목>" --body-file - <<'EOF'
<완성된 본문>
EOF
```

`--draft` 인자가 있으면 `--draft`를 붙인다. 대화 시스템이 PR attribution을 지정해 두었으면 본문 맨 끝에 빈 줄을 두고 그대로 붙인다.

### 7. 보고

최종 응답에 아래를 담는다. 다른 설명은 덧붙이지 않는다.

- PR URL
- 사용한 제목, 기본 브랜치, 템플릿(저장소 템플릿인지, 한글·영어 중 무엇인지)
- 체크하지 않은 테스트 항목 (작성자가 직접 확인해야 하는 부분이므로)
- 있으면: PR에 포함되지 않은 커밋 안 된 변경, 제외·중단한 사유

dry-run이면 PR을 만들지 않았다는 사실과 함께 제목과 본문 전문을 보여 준다.
