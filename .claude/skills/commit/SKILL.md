# commit

작업 트리의 변경사항을 읽고, 의미 단위로 나눠 한국어 커밋 메시지를 붙인 뒤, 사용자의 별도 승인 없이 바로 커밋한다. 사용자가 이 스킬을 부른 것 자체가 커밋해도 좋다는 뜻이기 때문이다.

승인 단계가 없는 만큼 분류와 메시지의 정확성이 중요하다. 커밋 전에 계획을 출력해 무엇을 어떻게 나눴는지 남기고, 커밋 후에는 결과를 확인해 보고한다. 잘못 나눴더라도 push 전이라면 사용자가 바로 고칠 수 있다.

## 절차

### 1. 변경사항 분석

먼저 저장소 상태를 확인한다. 아래 명령은 서로 독립적이므로 한 번에 실행한다.

```bash
git status --short
git diff HEAD            # staged + unstaged 전체
git log --oneline -10    # 이 저장소의 메시지 스타일 확인
```

- git 저장소가 아니면(`fatal: not a git repository`) 커밋할 수 없다고 알리고 멈춘다.
- 변경사항이 없으면 그렇게 알리고 멈춘다.
- untracked 파일은 `git diff`에 나오지 않는다. `git status`에서 `??`로 표시된 파일은 내용을 직접 읽어 무엇인지 파악한다.
- diff가 매우 크면 `git diff HEAD --stat`으로 전체 윤곽을 잡고, 파일별로 나눠서 읽는다.
- 이미 staged된 항목이 있으면 사용자가 의도해서 올린 것일 수 있다. 그 구성을 존중해 계획에 반영하고, 바꿔야 하면 계획에서 이유를 밝힌다.

diff를 읽는 목적은 파일 목록을 만드는 것이 아니라 **무엇을 왜 바꿨는지** 이해하는 것이다. 메시지의 품질이 여기서 결정된다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 이유로 설명되어야 한다. "A 기능 추가와 B 버그 수정"처럼 `와`로 이어야 설명되는 변경이면 둘로 나눈다. 나중에 `git revert`나 `git bisect`를 할 때 단위가 깔끔해야 하기 때문이다.

분류 기준:

- 서로 다른 목적(기능 추가, 버그 수정, 리팩터링, 설정 변경)은 분리한다.
- 같은 목적을 이루는 코드, 테스트, 타입, 스타일은 한 커밋으로 묶는다. 기능 코드와 그 테스트를 떼어 놓지 않는다.
- 같은 파일 안에 서로 다른 목적의 변경이 섞여 있으면 hunk 단위로 나눈다. 대화형 `git add -p`는 쓸 수 없으므로, 필요하면 `git apply --cached`로 patch를 부분 적용하거나, 나누기 어려우면 한 커밋으로 묶고 계획에서 그 사실을 알린다.
- 의존 순서를 고려한다. 앞 커밋만 체크아웃해도 빌드가 깨지지 않도록 기반 변경을 먼저 둔다.
- 변경이 작고 한 가지 목적이면 억지로 나누지 않는다. 커밋 1개가 정답일 때가 많다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

type은 아래 넷 중에서 고른다.

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능 추가·변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로이고 구조만 개선 |
| `chore` | 빌드, 설정, 의존성, 문서, 테스트 단독 변경 등 그 외 |

단, 1단계에서 본 `git log`가 `docs:`, `test:` 같은 다른 type을 일관되게 쓰고 있으면 그 저장소의 관례를 따른다. 저장소의 기존 관례가 이 표보다 우선이다.

요약 작성 규칙:

- 한국어로 쓰고, 50자 안팎의 한 줄로 끝낸다. 마침표는 붙이지 않는다.
- "무엇을 했는지"를 명사형이나 `~추가`, `~수정`, `~개선`처럼 짧게 끝맺는다. 예: `feat: 컴포넌트 생성 폼에 props 입력 필드 추가`
- diff를 읽어야만 알 수 있는 구체적 대상을 넣는다. `fix: 버그 수정`, `chore: 파일 수정` 같은 요약은 히스토리에서 아무 정보도 주지 않는다.
- 변경 이유가 diff만으로 드러나지 않으면(왜 이렇게 했는지, 어떤 증상을 고치는지) 빈 줄 뒤에 본문으로 한두 문장 덧붙인다. 자명한 변경에는 본문을 쓰지 않는다.
- 이슈·업무 번호는 사용자가 알려 준 경우나 브랜치명에서 명확히 읽히는 경우에만 넣는다. 추측해서 만들지 않는다.

예시:

```
feat: 컴포넌트 템플릿 선택 드롭다운 추가
fix: 빈 props 입력 시 생성 버튼이 활성화되던 문제 수정
refactor: 파일 생성 로직을 useGenerator 훅으로 분리
chore: eslint 규칙에 react-hooks/exhaustive-deps 추가
```

### 4. 커밋

승인을 기다리지 않고 바로 실행한다. 다만 커밋 직전에 계획 전체를 출력해, 사용자가 나중에 무엇이 왜 이렇게 나뉘었는지 확인할 수 있게 한다. 아래 형태로 보여 준다.

```
커밋 계획 (총 2개)

1. feat: 컴포넌트 템플릿 선택 드롭다운 추가
   - src/components/TemplateSelect.tsx
   - src/components/TemplateSelect.test.tsx

2. chore: eslint 규칙에 react-hooks/exhaustive-deps 추가
   - .eslintrc.json
```

계획을 출력한 뒤 커밋 단위마다 순서대로 실행한다.

```bash
git add <해당 커밋의 파일들을 경로로 명시>
git commit -m "<type>: <요약>" -m "<본문, 있을 때만>"
```

- `git add -A`나 `git add .`는 쓰지 않는다. 계획에 없는 파일이 딸려 들어가는 것을 막기 위해서다. 항상 파일 경로를 명시한다.
- 이미 staged된 파일 중 이번 커밋에 속하지 않는 것은 `git restore --staged <경로>`로 내린 뒤 진행한다.
- 대화 시스템이 커밋 attribution(예: `Co-Authored-By` 줄)을 지정해 두었으면 메시지 끝에 빈 줄을 두고 그대로 붙인다.
- pre-commit hook이 실패하면 `--no-verify`로 우회하지 않는다. 실패 원인을 보여 주고, 고칠 수 있으면 고친 뒤 **새 커밋**으로 다시 시도한다(`--amend`는 직전의 다른 커밋을 건드릴 수 있다).
- 모든 커밋이 끝나면 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인해 보고한다.
- push는 하지 않는다. 사용자가 따로 요청할 때만 한다.

## 커밋하면 안 되는 것

분석 중 아래에 해당하는 파일이나 내용이 보이면 계획에서 제외하고 사용자에게 알린다.

- `.env`, 개인키(`*.pem`, `id_rsa`), 자격 증명 파일, 토큰·비밀번호가 하드코딩된 코드. 보고할 때는 **값을 인용하지 말고 파일명과 줄 번호만** 알린다. 비밀 값이 대화 기록에 남지 않게 하기 위해서다.
- `node_modules/`, 빌드 산출물, 로그, `.DS_Store` 같은 생성물. `.gitignore`에 없다면 추가를 제안한다.
- 병합 충돌 표식(`<<<<<<<`)이 남아 있는 파일.

## 예외 상황

- **사용자가 메시지를 직접 지정한 경우** ("fix: ~로 커밋해줘"): 분석과 분류는 하되 메시지는 사용자 문구를 우선한다.
- **일부 파일만 커밋하라고 한 경우**: 범위를 그 파일들로 좁히고, 나머지는 건드리지 않는다고 계획에 명시한다.
- **merge/rebase 진행 중**: 충돌 해결 중인 상태에서는 임의로 커밋하지 말고 상황을 설명한 뒤 사용자에게 방향을 묻는다. 승인 없이 커밋하는 것은 평소의 정상 경로에만 해당하고, 이처럼 의도가 불분명한 상태에서는 묻는 쪽이 안전하다.
